# VågaFråga

A small class-coordination app: students sign up for an "active" role
(Curious Student / Interviewer) in a course session, and for observer
roles watching other students' sessions.

## Stack
- Static front end (`index.html`, `css/`, `js/`) — hosted on GitHub Pages.
- Firebase (Firestore + anonymous auth) as the shared data store — a
  visitor's browser talks to Firestore directly using the public web
  config in `js/firebase-config.js`; write access is governed by
  `firestore.rules`, not by keeping that config secret.

## Two Firebase projects — production and test are kept separate
- **`vagafraga`** (alias `prod`) — the real project. `js/firebase-config.js`
  always points here; this is what the live GitHub Pages site uses.
- **`vagafraga-test`** (alias `test`) — a separate project for trying things
  out, with its config archived in `test-env/firebase-config.test.js`. It
  has its own Firestore data, entirely isolated from production.

To test locally against the test project: copy `test-env/firebase-config.test.js`'s
contents over `js/firebase-config.js`, run a local server, and copy them
back (or `git checkout js/firebase-config.js`) before committing anything —
never let a commit point the live site at the test project.

To deploy Firestore rules to one or the other explicitly:

    npx firebase-tools deploy --only firestore:rules --project prod
    npx firebase-tools deploy --only firestore:rules --project test

## Data
- `data/courses.json` — course code + name list.
- `data/schedule.json` — session instances (course, date, slot 0-3, type).
  Both are generated by `scripts/timeedit_to_schedule.py` from a TimeEdit
  `.ics` export plus the MaFyCourses course catalog (see below) — don't
  hand-edit them; re-run the script instead.

## Regenerating the schedule
    python3 scripts/timeedit_to_schedule.py \
      --ics /path/to/timeedit-export.ics \
      --catalog "/path/to/MaFyCourses.catalog.json"

The catalog file is read at run time and never copied into the repo (it
holds full syllabus text with no reason to be public) — only the course
code + short name derived from it end up in `data/courses.json`. The
script reports any course name it couldn't match in the catalog, and any
kept-type session whose time didn't land on one of the app's four fixed
daily slots, instead of silently guessing.

Activity types kept, and the term window, are constants at the top of the
script (`KEEP_ACTIVITIES`, `FIRST_MONDAY`/`LAST_FRIDAY`) — edit those and
re-run if the selection needs to change. `FIRST_MONDAY`/`LAST_MONDAY` must
stay in sync with the same constants in `js/app.js`.

## Firestore collections
- `students/{slug}` — one record per registered name.
- `sessions/{course}_{date}_{slot}` — who's doing what in a given
  course/date/timeslot; this is what the calendar boxes are colored from.
- `meta/counters` — running totals used for the active-role balance rule.
- `customCourses/{code}`, `customSchedule/{id}` — courses/sessions added
  live by students via "Add another course", merged into the picker and
  calendar alongside the static data above.

## Local preview
Any static file server works, e.g. from this folder:

    npx serve .

## Deployment
Pushed to GitHub, served via GitHub Pages from the repo root.
